# Evaluation reports

Generated by the ML evaluation harness. Two artefacts per task:

| File | For | Contents |
|---|---|---|
| `<task>_eval.md` | humans | baseline-vs-model comparison + per-class breakdown |
| `<task>_metrics.json` | CI | machine-readable metrics, used as the regression baseline |

Regenerate with:

```bash
python -m app.eval.harness --task resolver
python -m app.eval.harness --task guard
```

CI runs the same commands with `--check-baseline`, which **fails the build** if a
predictor's macro F1 drops below the committed JSON. Re-baselining is therefore an
explicit act: change the labels, rerun without the flag, and commit the new
numbers so the diff is reviewable.

## The dataset

`data/labels/deals.csv` — **115 real listings** drawn from the scraper database
(stratified: up to 5 per resolved product, plus the unresolved long tail and the
rows the rule guard flagged). Labels are a human reading of each title, **not**
the pipeline's own output; copying the pipeline's output would make the
evaluation circular.

Labeling rubric (`product_label` / `guard_label`):

- **product_label** — the tracked registry product if the listing *is* that
  product, else `__none__` (untracked model, whole system, junk, service).
- **guard_label `keep`** — a genuine single unit of one hardware item being sold
  (a standalone part, a console/phone, or a laptop).
- **guard_label `reject`** — accessory/part, multi-unit lot or bundle, "for
  <platform>", a whole desktop/PC/workstation (whose component the resolver would
  otherwise price), for-parts/repair, or a non-hardware ad.

Split: hash-group by normalised title (70/15/15), so the same title can never
appear in both train and test — plus a **stratification pass** that promotes a
group into `train` for any label that would otherwise have no training example.
(That guarantee moves a few groups, so the guard test set is 35 rows and the
resolver's is 30 — the resolver's label space is wider, so it needs more
promotions.)

## Results

**Product resolver**

| Predictor | Accuracy | Macro F1 |
|---|---|---|
| `resolver-baseline` (rules) | 0.733 | 0.844 |
| `tfidf-linear` | **0.867** | **0.871** |
| `hybrid-resolver` | 0.733 | 0.844 |

**Listing guard**

| Predictor | Accuracy | Macro F1 |
|---|---|---|
| `guard-baseline` (rules) | 0.829 | 0.790 |
| `guard-model` (rule-informed) | 0.829 | 0.816 |
| `hybrid-guard` | **0.857** | **0.849** |

## Interpretation (say this, not more)

- **The resolver model now beats the rules — after two fixes the labeling
  exposed.** It scores 0.871 macro F1 / 0.867 accuracy against the rules' 0.844 /
  0.733. Before those fixes it lost badly (0.484), and the causes were data
  artifacts, not the algorithm.
- **The rules-first hybrid does *not* capture that gain, by design.** It only
  rewrites titles the rules *abstain* on, but the model's wins are on titles the
  rules resolve **confidently and wrongly** (a `GTX 1080` read as a `GTX 1660
  Super`, an Intel `MacBook Pro` read as an M1). So the report shows the
  standalone model as the upside and keeps the hybrid conservative
  (`resolver_min_confidence = 0.8`) as the safe deployment option. Rules-first vs
  model-primary is a product decision, and it is stated rather than hidden.
- **The guard is where ML wins outright.** The rule guard has no keyword for
  `controller`, `carry case`, `charger`, a "Buying ..." wanted ad or a printing
  service. Feeding its own pattern hits in as *features* lifts the hybrid to 0.849
  macro F1 (rules: 0.790) at higher accuracy.
- **A split artifact was the model's real problem.** A hash-only split let four
  classes (`GTX 1080`, `GTX 1080 Ti`, `MacBook Pro M3`, `RX 6800 XT` — 7 of 35
  test rows) fall entirely outside train, where no model can predict them and
  they score F1 = 0. The split is now stratified by label and guarantees every
  label a training group; that change alone took the model from 0.484 to 0.871.
- **Two bugs the labeling surfaced, both fixed.**
  1. *Bare-numeric aliases.* `iPhone 15` / `iPhone 14` carried the aliases `"15"`
     and `"14"`, so any title containing those digits resolved to an iPhone — a
     `Dell XPS 15`, a `ThinkCentre M715q`, an `iMac 2015`. Numeric aliases shorter
     than four digits are now forbidden, enforced by a registry invariant test.
  2. *Macro F1 averaged phantom classes.* Classes with support 0 — predicted but
     never true — were scored as hard zeros and dragged the baseline from 0.776
     to 0.597. Macro F1 now averages only over classes present in the true labels.
- **These numbers are still noisy.** 115 rows (30 resolver / 35 guard in test)
  means rare classes carry 1–2 test examples each. This demonstrates the
  *method*, not a production-accuracy claim.

## Price model (asking-price band)

Regenerate with:

```bash
python -m app.eval.price_harness
```

Predicts the **P25 / P50 / P75 of comparable asking prices** — never a market
value. The split is **temporal** by `date_posted`: train on the oldest listings,
test on the newest, which is how the model is used in practice (predict newly
posted listings from older history).

| Predictor | MAE (P50) | P25–P75 coverage |
|---|---|---|
| `product-quantile-baseline` | **$284** | 0.30 |
| `lightgbm-quantile` | $404 | 0.36 |

**Interpretation:**

- **The simple per-product empirical quantile still beats LightGBM on MAE**
  ($284 vs $404) with 200 training rows. The gap narrowed when the corpus grew
  (it was $344 vs $502 on 86 rows), which is the expected direction — but the
  boosted model has not overtaken a per-product median yet. **Data, not
  modelling, remains the lever.**
- **Model capacity has stopped mattering.** A sweep on the current data:
  7 leaves / 150 trees → **$404** (coverage 0.36); 15 / 300 → $398 (coverage
  0.25); 31 / 600 → $408 (coverage 0.27). MAE is flat across a 4× capacity
  range, so the default keeps the *small* model because it is better calibrated
  and cheaper — not because bigger is worse.
- **Coverage is the interesting part.** The baseline's P25–P75 band contains only
  **30%** of the newer listings against a target of 50%. Under a *random* split
  it would sit near 50% by construction — so the temporal split is measuring real
  drift between older and newer listings, and a random split would have hidden
  it. That is exactly what time-based validation is for.
- LightGBM's band is better calibrated (0.36 vs 0.30) but less accurate: a
  genuine precision/calibration tradeoff, not a win.
- The **new-retail ceiling is wired in** (`data/retail_prices.csv`, format in
  `data/retail_prices.sample.csv`) but **off** here because no reference file
  exists yet — 0 rows capped, so the ceiling costs nothing and proves nothing.
- **267 usable rows** after re-resolving titles and IQR-trimming (up from 115
  before the Canada-wide run). Note the composition caveat too: the product mix
  shifts with posting age, so any age→price effect is partly mix, partly
  survivorship (a one-shot scrape only sees listings that didn't sell).
- **Volume grew faster than usable volume.** The corpus went 625 → 1,577 rows
  but the resolved, priceable share only went 115 → 267, because a Canada-wide
  broad-term sweep drags in a long tail of out-of-scope listings (see the
  unresolved-share note in `PROJECT_STATUS.md` §5).

**To move this forward:** a deeper Canada-wide scrape for volume, and daily runs
to add a repeated-observation axis — which is what unlocks price-cut detection
and time-to-sell, both invisible to a single snapshot.
